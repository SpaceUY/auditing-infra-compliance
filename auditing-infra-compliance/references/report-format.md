# File and report formats

Loaded before writing `scope.json`, `vault-claims.json` or `verification-claims.json`, and when reading `findings.json` or `verification.json`. Claude **writes only three files** (`scope.json`, `vault-claims.json`, `verification-claims.json`); everything else is generated by the scripts and is not edited by hand.

## 1. Run folder

`./compliance-reports/<platform>-<scope>-<YYYY-MM-DD-HHMM>/` in the working directory, never inside the vault (`assemble_findings.py` ends with `error: the run directory is inside the vault (<root>): reports are never written inside the vault, use a folder outside it` and exit `2` when the run folder is inside the `root` of `vault-index.json`; `render_report.py` refuses in the same way an output inside the root recorded by a `vault-index.json` next to `findings.json`: "the report output is inside the vault …"). Example: `compliance-reports/acme-notes-feature-email-2026-11-12-1030/`.

| File | Written by |
|---|---|
| `scope.json`, `vault-claims.json`, `verification-claims.json` | Claude |
| `vault-index.json` (includes `sensitive_files`) | `vault_index.py index` |
| `checks-result.json`, `inventory.json`, `raw/<CHECK_ID>/…` | `collect.py` (see "Partial result" below) |
| `findings.json` | `assemble_findings.py` |
| `verification.json` | `verify_remediation.py` |
| `report.html` | `render_report.py` |

Everything that is written is masked: `AKIA…WXYZ` (last 4 characters), emails `u***@domain` (except those of the `VantaOwner` tag), secrets `[REDACTED]`. Besides AWS keys, secrets cover: values after password labels in any format (`password: x`, table cells `| DBPassword | x |`, `MasterUserPassword`, `db_password`, `contraseña`, `--master-user-password x`; an unquoted value runs to the end of the line or cell, a quoted one to the closing quote), `api_key`, `token` / `access_token` / `auth_token` / `x-amz-security-token`, `client_secret`, `Bearer <token>` and a URL's password (`scheme://user:password@host`). References are not secrets and stay as they are: "in Secrets Manager" (or "en Secrets Manager"), "see …", `${VAR}`, `{{…}}`, `<…>`, `N/A`, `-`, empty, `*****`, `[REDACTED]`, Secrets Manager or SSM ARNs, `*_file` / `*_path` labels and password-policy settings (length, age, reuse). A table header row is not a credential. Detection has known limits (`references/vault-reading.md` §9): a person must review the flagged notes and the unflagged ones.

No sources, no report: if there is no vault index, no claims and no AWS credentials (`checks-result.json` with `aws: null`), `assemble_findings.py` ends with exit `2` and the message "no sources: a vault or read-only AWS credentials are required", and does not write `findings.json`.

**Partial result.** `collect.py` writes `inventory.json` as soon as the inventory finishes and `checks-result.json` before the checks and every ~15 s; while it is not finished it carries `"partial": true` and `"pending_checks": [<ids>]`, and a complete run has no `partial`. If it is interrupted (Ctrl-C, SIGTERM, Bash timeout) the partial file stays on disk and the exit is `130` (`0` complete, `2` no credentials). `assemble_findings.py` turns `partial` and `pending_checks` into a `findings.json` warning ("PARTIAL result: the collection was interrupted (checks not finished: A, B); what is missing is not verified: re-run collect.py") that the HTML shows with the others. Additive fields: `aws.blocked_regions` (regions whose inventory an SCP denied; they are dropped with a warning and `assemble_findings.py` adds them to the warnings as "blocked by SCP in regions X, Y: their resources were not verified"), `failed_calls[].item` and `.reason`, and in the rows `detail.reason` "blocked by SCP" (with `missing: []`: no profile permission is missing). A region whose calls fail ends up `NOT_VERIFIED` per region; the healthy ones keep their `FAIL`/`PASS`, and there is no account-level `PASS` if any region failed.

### 1b. `NOT_VERIFIED` reasons in the rows of `checks-result.json`

Never `PASS` or `FAIL` when something could not be read. `detail.reason` (and `missing`, the missing permission) says why:

| Reason | When |
|---|---|
| missing permission (`missing: ["service:Action"]`) | `AccessDenied` on a call |
| "could not list the regions" | `ec2:DescribeRegions` failed: the checks that span all regions end up `NOT_VERIFIED` (with `missing: ["ec2:DescribeRegions"]` if it was `AccessDenied`) and no regional call is made for them; with `regions: "auto"` the same goes for every account check with a regional call (DET-003, DET-004, DET-006, DET-007, DAT-010): never `PASS` for looking only at `us-east-1`. **Resource** checks may keep the `PASS`/`FAIL` rows of the resources listed in `us-east-1` next to the `NOT_VERIFIED` row (region `null`) of the regions that could not be listed; with that row the verdict is never `OPTIMAL`. Checks with no regional call and those for regions explicitly listed in `scope.regions` carry on. In `auto` only `us-east-1` is inventoried and each regional type carries a row with region `null` |
| "no regions in scope" | a regional check with no region to walk (for example all blocked by SCP): never a vacuous pass |
| "incomplete inventory" (`missing: ["inventory:<type>"]`) | listing a type in a region failed: one row per (type, region) next to the `PASS`/`FAIL` rows of the regions that were listed; never `N/A` after a failed listing |
| "blocked by SCP" | an SCP denies the read; no profile permission is missing (`missing: []`) |

**"Context" CMP-006 rows**: after the checks, `collect.py` also evaluates CMP-006 for the instances attached to a security group with NET-001..004 `FAIL` rows, even if nobody put them in the scope (it is the evidence conflict rule CR-003 asks for). Those rows carry `detail.context_for: [<NET ids>]`; they are not a finding the user asked for.

## 2. `scope.json`

```json
{"platform": "Acme Notes", "mode": "feature", "target": "email sending",
 "regions": "auto", "profile": null,
 "resources": [
   {"type": "ses_identity", "id": "acme-notes.example", "region": "us-east-1"},
   {"type": "lambda_function", "id": "acme-notes-mailer", "region": "us-east-1"}
 ],
 "domains": null}
```

| Field | Value |
|---|---|
| `platform` | Readable name. |
| `mode` | `full` \| `feature` \| `resource`. |
| `target` | `null` in `full`; the feature text or the resource id/ARN. |
| `regions` | `"auto"` (enabled ones with resources + `us-east-1`) or a **non-empty** list of region names, e.g. `["us-east-1", "eu-west-1"]`. A region that is not enabled is skipped with a warning. Any other shape (empty list, loose string, names that are not regions) or no enabled region makes `collect.py` end with exit `2` and a message, without writing files. |
| `profile` | AWS profile (`AWS_PROFILE`) or `null` for the already configured environment. It is a profile name, never a key. |
| `resources` | `[]` in `full`. In `feature` and `resource`: `{type, id, region}` objects; `type` is a key of `references/inventory.json` and `id` the id, name or ARN (mapping table in `references/vault-reading.md`). |
| `domains` | `null` (all) or a list to narrow: `compute`, `data`, `detection`, `email`, `encryption`, `iam`, `integration`, `inventory`, `logging`, `monitoring`, `network`. |

These also end with exit `2` and a message, before any call to AWS and without writing files: a missing `mode` or one that is not `full`/`feature`/`resource`, `domains` that is not `null` or a list of names, a domain that does not exist in the catalog, an empty `resources` or one with elements lacking a text `type`/`id` in `feature`/`resource` mode, or a `scope.json` that is not an object. A well-formed scope that no check covers (types such as `sns_topic`, `subnet`, `launch_template`, `apigw_http_api`, `wafv2_web_acl_cloudfront`, or a `domains` filter that leaves them out) does **not** end with exit `2`: `collect.py` exits with `0`, writes `checks-result.json` with `results: []` and the warning "no catalog check applies to: <types>", and `assemble_findings.py` lists those components in `unverified_scope` with verdict `NOT_VERIFIABLE`.

`scope.json` is saved in the run folder (`$RUN/scope.json`) and is **neither moved nor deleted** before assembling: `assemble_findings.py` reads it from there (`unverified_scope`). `collect.py` only runs the read operations of `catalog.REVIEWED_OPERATIONS` (`references/remediation-guidelines.md` §1).

In `feature` and `resource`, collect picks the resource checks whose type is in `resources` and the account checks that declare that context, and filters the offenders to those resources.

## 3. `vault-claims.json`

A list of objects. All fields except `kind` may be `null` or omitted.

```json
[
  {"kind": "DRIFT", "check_id": "DAT-007",
   "resource": {"type": "s3_bucket", "id": "acme-notes-uploads", "region": "us-east-1"},
   "vault_note": "systems/Uploads Bucket.md",
   "vault_claim": "The uploads bucket blocks all public access",
   "actual": "Block Public Access disabled",
   "severity": null, "breaks_tests": []},
  {"kind": "EVAL", "check_id": "IAM-013", "resource": null,
   "status": "PASS", "detail": {"reason": "Administrative policies are limited to one emergency role"}}
]
```

| Field | Meaning |
|---|---|
| `kind` | `DRIFT` \| `UNDOCUMENTED` \| `DOCUMENTED_ONLY` \| `DOCUMENTED_GAP` \| `EVAL`. Any other value is ignored with a warning. |
| `check_id` | Catalog id (`DAT-007`) or `null` for an observation outside the catalog. A non-existent id generates a warning. |
| `resource` | `{type, id, region}` or `null`. If the region of a regional resource is not known, leave `region: null` (do not guess): it stays `__FILL_IN_REGION__` and is mentioned in the answer; for account/global it is `us-east-1`. |
| `vault_note` | Path of the note (or evidence file) the claim comes from. Text or `null`. |
| `vault_claim` | What the vault says, verbatim or briefly paraphrased. Text or `null`: any other type ends `assemble_findings.py` with `error:` and exit `2`. |
| `actual` | What was observed in the account (or "not verified: no credentials"). Text or `null` (same `error:` / exit `2` otherwise, as for `vault_note`). |
| `severity` | `critical` \| `high` \| `medium` \| `low` or `null`. Priority: `detail.severity_override` > the claim's `severity` > catalog severity (`low` for `UNDOCUMENTED` and claims with no check). |
| `actual_status` | `DRIFT` or `UNDOCUMENTED` only: `"FAIL"` if reality violates the check; then the finding keeps the complete fix and counts as a failure (see `summary`). Without this field (or with another value) it carries no commands or steps. On any other kind (`DOCUMENTED_ONLY`, `DOCUMENTED_GAP`) it is ignored and the finding gets the warning "<KIND> claim for <check_id>: actual_status FAIL ignored (only DRIFT and UNDOCUMENTED claims use it)"; a claim promoted to `DRIFT` by `breaks_tests` does use it. |
| `breaks_tests` | `[{"tool": "drata", "test": 30}]` or `[{"tool": "vanta", "test": "<name>"}]` if a vault recommendation would break those tests. It turns the claim into a `DRIFT` of at least `high` severity. |
| `status`, `detail` | `EVAL` only: `status` is a valid status (`PASS`, `FAIL`, `N/A`, `NOT_VERIFIED`), `detail.reason` the justification. |

**EVAL:** resolves the `PENDING_CLAUDE` row with the same `check_id` (the `resource` must match, unless the row is the account-level one). One `EVAL` `FAIL` can be written per offending resource. Without a claim, the row stays `NOT_VERIFIED` with a warning. The findings of an `EVAL` come out marked "evaluated by Claude".

**Observation outside the catalog:** `check_id: null`, `kind` `UNDOCUMENTED` or `DOCUMENTED_GAP`, and in `actual` or `vault_claim` the phrase "Claude observation, outside the catalog". It never carries remediation commands or mappings of its own.

## 4. `findings.json` (assembler output)

Top-level keys: `meta`, `summary`, `findings`, `dependencies`, `coverage`, `warnings`, `notes`.

- Findings that come out on their own from the vault index: each `secrets_detected` and each `sensitive_files` entry (`.env*`, `*.pem`, `*.key`, `*credentials*`, detected by name only) generates a `FAIL` `critical` with `check_id: null` and `console_only` remediation (rotate and remove the file).
- `meta`: platform, mode, target, date, `lang` (`--lang` only accepts `en`; the report is English only), `tool` (`--tool drata|vanta|both`; `null` if not given: the HTML preselects `drata` or `vanta` in the tool filter, `both` and `null` preselect nothing, and both remain available), `catalog_checks`, `vault` (`path`, `kind`), `aws` (`account_id`, `identity_arn`, `regions`; `null` without credentials).
- `summary`: `verdict`, `verdict_basis`, `verdict_text`, `verdict_reasons`, `aws_verified`, `unverified`, `by_status`, `by_severity_fail`, `drata_tests_failing`, `vanta_tests_failing`, `not_verified`. **There is never a percentage or a grade.** `by_severity_fail`, `drata_tests_failing` and `vanta_tests_failing` count every `FAIL` and every `DRIFT`/`UNDOCUMENTED` with `actual_status: "FAIL"` (their `status` stays `DRIFT`/`UNDOCUMENTED`; `by_status` counts the status as written), and a control touched by such a finding is `FAIL` in `coverage`. The HTML counters follow the same rule. Every string of `summary` and `unverified_scope` is masked like the rest (emails stay).
  - **`verdict_basis`** says what the verdict rests on: `aws` (there were credentials and the vault was not used), `vault` (no credentials) or `aws+vault`. An `EVAL` claim only judges AWS data and does not count as vault. `verdict_text` always names the basis: "Optimal based on what the vault documents (not verified against AWS)", "Not optimal based on AWS: …", "Optimal based on AWS and the vault". With basis `vault` the text never says AWS verified anything, and the `DOCUMENTED_*` statuses do not change (nothing is marked `PASS` or `FAIL` because of what the vault says); only the global verdict uses the vault as its basis.
  - `verdict` is exactly one of `NOT_OPTIMAL`, `NOT_VERIFIABLE` and `OPTIMAL`. Order: `NOT_OPTIMAL` > `NOT_VERIFIABLE` > `OPTIMAL`. `verdict_reasons` separates failures ("N failing finding(s)") from critical or high documented gaps ("the vault says so, not verified"). The HTML shows the basis next to the verdict.
    - **Basis `aws` or `aws+vault`:** `NOT_OPTIMAL` with any `FAIL`, any `DRIFT` or `UNDOCUMENTED` finding with `actual_status: "FAIL"` or a `critical`/`high` `DOCUMENTED_GAP`. `NOT_VERIFIABLE` with no evaluated `PASS` or `FAIL`, a `DRIFT` created by `breaks_tests` without an `actual_status` that checks the real state, a partial run, regions blocked by SCP, incomplete inventory, or anything unverified (`NOT_VERIFIED`, `DOCUMENTED_ONLY`, `DOCUMENTED_GAP`, scope components without claims). `OPTIMAL` if none of the above (with `DRIFT` or `UNDOCUMENTED` without a proven failure, the text says so).
    - **Basis `vault` (no credentials):** `NOT_OPTIMAL` with a `critical`/`high` `DOCUMENTED_GAP`, a secret or sensitive file (`FAIL`) or a claim with `actual_status: "FAIL"`. `OPTIMAL` if there is at least one documented control (`DOCUMENTED_ONLY`) in scope, no `DOCUMENTED_GAP` (of any severity), no unresolved `DRIFT`/`UNDOCUMENTED`/`NOT_VERIFIED` and an empty `unverified_scope`. Otherwise `NOT_VERIFIABLE`, and `verdict_reasons` says which components or controls the vault does not document.
  - `unverified`: counts `not_verified`, `documented_only`, `documented_gap`, `scope_without_claims` and `total`. Without credentials the HTML shows it instead of zeros that would read as "clean".
- `unverified_scope[]` (top level): `scope.json` components with no finding at all (except `N/A`): `{type, id, region, reason}`; the HTML lists them as "not verified". The assembler reads `scope.json` from the run folder if it is there. A component given by ARN, name or id is resolved against `inventory.json` (`id`, `arn`, `name` of an item of the same `type`, as `collect.py` does), so an ARN whose last segment differs from the inventory id (ALB, WAF web ACL, secret) still counts as covered by that item's findings.
- `findings[]`: `id` (`F-0001`…), `check_id`, `title`, `domain`, `status`, `severity`, `resource` (`type`, `id`, `region`, `name`), `evidence`, `vault_claim`, `vault_note`, `mappings`, `remediation`, `evaluated_by` (`script` \| `claude` \| `vault`: `vault` marks `DOCUMENTED_ONLY` and `DOCUMENTED_GAP`, which are transcribed vault claims, not an evaluation), `actual_status` (`"FAIL"` on a `DRIFT`/`UNDOCUMENTED` whose real state fails; otherwise `null`), `vacuous`, `breaks_tests`, `missing` (missing permissions), `depends_on_me` (tests that depend on the resource).
- **Fix by status:** `FAIL`, `DOCUMENTED_GAP` and a `DRIFT` or `UNDOCUMENTED` with `actual_status: "FAIL"` carry the complete fix. `DOCUMENTED_ONLY`, `PASS`, `N/A`, `NOT_VERIFIED` and the other `DRIFT` and `UNDOCUMENTED` carry `remediation.steps: []`, `commands: []`, `notes: ""`, `kind`, `risk` and `downtime` as `null` (there is nothing to apply), only `verify_after` (the HTML shows it as "Verify with") and `remediation.note_status` = "not verified: do not apply without confirming" (a `PASS` and an `N/A` carry their own note: "verified in AWS: compliant, no fix needed (the command is only useful to re-check it)" / "does not apply in this scope: no fix needed").
- **`DOCUMENTED_ONLY`:** severity always `low`; the check's own stays in `evidence.catalog_severity` together with `evidence.note: "not verified"` and the HTML says "check severity: high, not verified".
- `mappings`: `drata` (`test`, `name`, `source`), `vanta`, `tsc` and `iso27001_2022` (`id`, `sourced`), `security_hub`, `cis_aws`.
  - `sourced: "drata-dcf-2026-11-12"` = authoritative mapping taken from Drata's DCF catalog.
  - `sourced: false` = **inferred**; the HTML marks it "inferred".
- `dependencies[]`: resources that currently passing tests depend on ("do not touch without review").
- `coverage`: Annex A and TSC with status `FAIL` \| `NOT_VERIFIED` \| `PASS` \| `NOT_TOUCHED` and category (`organizational`, inherited from AWS…). A control touched only by `DOCUMENTED_ONLY` or `DOCUMENTED_GAP` findings is listed `NOT_VERIFIED` (the vault says so, nobody checked). Organizational ones come out as "outside the scope of this report", except those a finding touches: those are listed separately as "mentioned by findings" with their status (the report does not evaluate them).
- `warnings`: besides those of the run, "untyped vault: the component map is inferred and less reliable" with a free-form vault, and the notes that were read truncated (`vault-index.json` → `truncated_notes`).

### Statuses

| Status | Meaning |
|---|---|
| `FAIL` | Verified live, does not comply |
| `PASS` | Verified live, complies |
| `DRIFT` | The vault claims something different from reality |
| `DOCUMENTED_ONLY` | Vault only: says it complies, not verified |
| `DOCUMENTED_GAP` | Vault only: says it is missing or `proposed` |
| `UNDOCUMENTED` | Exists in the account and the vault does not mention it |
| `NOT_VERIFIED` | No credentials or `AccessDenied` (with the missing permission) |
| `N/A` | Does not apply; with `vacuous: true` = vacuous pass (there are no resources of that type). **Never `PASS`.** |

### Severities

| Severity | When |
|---|---|
| `critical` | Public exposure of data or credentials; root without MFA or with access keys |
| `high` | A Drata or Vanta automated test fails |
| `medium` | A Security Hub, CIS or FSBP control fails with no direct Drata/Vanta test |
| `low` | Hygiene |

## 5. The `{resource_id, detail}` convention of JMESPath checks

For whoever reads or extends the catalog: the `verify.offenders` expression of a `jmespath` check is passed as `--query` and **projects a list of `{resource_id, detail}` objects**; each one is an offender and the empty list is `PASS`. `resource_id` may be omitted when the call has `for_each` (the iterated value is used); an element that is not an object is taken as the `resource_id`. `detail` goes to `evidence`. A `detail.severity_override` changes that offender's severity. Claude does not re-evaluate PASS/FAIL of these checks.

## 6. `verification.json` (output of `verify_remediation.py`)

- `per_finding` (every finding that carries a fix: `FAIL`, including console-only ones, and any other with commands or steps, such as `DOCUMENTED_GAP`; those that only carry "Verify with" (`note_status`) are not included): `{"F-0005": {"status": "OK|REVIEW|CONFLICT", "issues": [{"kind", "message", "source", "rule_id"}]}}`.
- `conflicts`: conflicts between fixes (rules in `references/conflict-rules.json`).
- `gaps`: what is missing (`FAIL` with no commands that is not `console_only`, `NOT_VERIFIED` with a missing permission, inventory resources with no check, fixes with no `verify_after`, missing evidence for a rule —e.g. an instance that uses the security group with no `CMP-006` result—, and "no AWS credentials: no state was verified against AWS").
- `apply_order`: finding ids in the suggested order of application (identity, logging and detection, KMS keys, encryption, network, data and backups, monitoring, tags and integration; by severity within each group and `planned_change` last; an "A before B" rule wins).
- `fill_in_pending` (counts the `__FILL_IN_*__` in commands, steps, `verify_after` and notes, and the `verify_after` of verify-only findings, which is also pasted), `cli_checked` (only `true` if at least one operation was compared), `cli_requested`, `cli_operations_checked`, `summary` (`OK`, `REVIEW`, `CONFLICT`), `warnings`.
- Observation kinds (`issues[].kind`): `syntax`, `invalid_cli`, `unresolved_placeholder`, `hygiene`, `requires_fill_in`, `destructive_without_warning`, `dependency_impact`, `downtime`, `high_risk`, `missing_evidence`, `rule_conflict`, `claude`.
- `findings_digest`: fingerprint of the whole `findings[]` list of `findings.json` (every field of every finding, keys sorted: evidence, severity, `depends_on_me`, resource, `actual_status`, fix...); `meta`, `summary` and the warnings are not part of it. `render_report.py` compares it: if it does not match (`assemble_findings.py` was re-run) or there is no fingerprint (`verify_remediation.py` always writes it), it ignores the verification and the report shows "stale verification: re-run verify_remediation".
- A fix with `remediation.downtime: true` never stays `OK`: the floor is `REVIEW` ("the fix declares downtime"). Nor does a `risk: high` fix stay `OK` ("high risk: pending review against the vault before applying"), nor one that lacks the evidence a rule needs (`missing_evidence`).

List what Claude must review (read-only; only the findings present in `per_finding`: a verify-only finding carries no fix to review and its `risk` is `null`):

```bash
python3 - "$RUN" <<'PY'
import json, sys
run = sys.argv[1]
f = json.load(open(f"{run}/findings.json"))["findings"]
v = json.load(open(f"{run}/verification.json"))["per_finding"]
for x in f:
    r = x.get("remediation") or {}
    s = v.get(x["id"], {}).get("status")
    if x["id"] in v and (s in ("REVIEW", "CONFLICT") or r.get("risk") in ("medium", "high")):
        print(x["id"], s, r.get("risk"), x["check_id"], x["resource"]["id"])
PY
```

## 7. `verification-claims.json`

```json
[
  {"finding_id": "F-0006", "status": "REVIEW",
   "message": "The acme-notes-uploads bucket is used by the attachments service according to systems/Uploads Bucket.md.",
   "vault_note": "systems/Uploads Bucket.md"},
  {"finding_id": "F-0003", "status": "OK", "message": "No dependencies in the vault.", "vault_note": null}
]
```

`status`: `OK` \| `REVIEW` \| `CONFLICT`. `message` and `vault_note` are text or `null`. The script combines both sources and **the most severe status wins**: a claim never lowers a script `CONFLICT`. An `OK` changes nothing; a `status` outside `OK`\|`REVIEW`\|`CONFLICT` is treated as `REVIEW`; a claim with an invalid shape or with a `finding_id` that has no fix to verify is ignored with a warning; if the claims file does not exist, `verify_remediation.py` carries on without claims and warns (invalid JSON is an error).

## 8. What the user sees in the HTML

The filters are remembered in the browser per report (key made of the report's `generated_at`, platform, mode, target and account), never shared between reports, and the `--tool` preselection overrides a remembered tool. Header, summary (counts by status and severity, affected Drata/Vanta tests, list of what is not verified; no percentage), filters, cards by severity with mapping chips (marked "inferred" where applicable), evidence, what the vault claims, a remediation block with Copy ("Copy all" only on `cli` fixes with more than one block; `cli_with_decision` and `planned_change` are copied block by block, never all at once), verification stamp, the verdict (`Optimal` / `Not optimal` / `Not verifiable`) at the very top, an explicit notice when there were no AWS credentials (nothing was verified against AWS, counts of what is documented and unverified instead of zeros, scope components "not verified"), the "Copy low-risk fixes" button (only with a current verification and only what stayed `OK`; without a verification or with a stale one it appears disabled with the reason), the "stale verification" notice if `findings.json` was re-assembled after verifying (repeat `verify_remediation.py`), "Do not touch without review", standards coverage, run warnings and the footer "Automated technical pre-audit. It is not an audit opinion and does not cover organizational controls (policies, HR, teams, vendors, ISMS).". Language: English; IDs, commands and test names stay in their original language.
