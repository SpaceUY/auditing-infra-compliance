# Remediation: rules for the CloudShell commands

Loaded when reviewing the fixes (step 9), when explaining to the user how to apply them and when someone says "fix it yourself". **The fixes live in the catalog** (`references/checks/<domain>.json`, `remediation` field) and the assembler instantiates them in `findings.json`. Claude does not write, edit or "improve" commands: it reviews them, explains them and flags them.

## 1. Absolute rule: this skill never writes to AWS

- **This skill only produces a report** (is the infrastructure optimal for SOC 2 / ISO 27001, Drata/Vanta?) with remediation commands for **a person** to paste into CloudShell. **Neither Claude nor the scripts write to AWS or apply a fix, under any circumstance**: not even if the user asks, not "just to test", not with another tool (console, MCP, SDK, another profile), not by offering access, a PR or IaC.
- Do not offer "to apply it if you give me access", "to prepare a PR", "to generate the Terraform/CDK" nor ask for a write profile. The answer to "fix it yourself" is: I do not execute changes; the report brings each fix with a Copy button, the verification stamp and the suggested order.
- The commands are written to `findings.json` and the HTML; a person pastes them into AWS CloudShell after reading them.
- **An admin profile changes nothing:** if the user offers one ("use my admin profile", "I authorize you"), Claude may only use it for the read-only collection the scripts allow (with the `AdministratorAccess` warning and the `SecurityAudit` + `ViewOnlyAccess` recommendation) and never to apply a fix. If there is no verified fix (no credentials, everything `DOCUMENTED_*`), there is no Copy block to point to: say that there is nothing verified to fix.
- **How read-only is guaranteed:** `aws_runner.py` (used by `collect.py`) only admits `describe-*`, `list-*` and `get-*` (plus `lookup-events`, `generate-credential-report` and the narrow exception `inspector2 batch-get-account-status`), rejects a denylist of reads that expose secrets or data and any operation whose name is sensitive (credential, password, token, secret, private-key, embed-url, download-url, access-details, records, shard-iterator) except for the reviewed exceptions (`SENSITIVE_NAME_EXCEPTIONS`: the credential report, the password policy, `list-service-specific-credentials`, `secretsmanager list-secrets`/`describe-secret`/`list-secret-version-ids`), and the `--include-value(s)` flags. In addition, `catalog.REVIEWED_OPERATIONS` is the reviewed list of (service, operation) pairs: `validate_catalog.py` rejects a check or an inventory type with a pair that is not there ("not reviewed") and `collect.py` executes none outside the list, even if someone edits the catalog. Adding a new call requires adding the pair to that list.
- `verify_remediation.py` does not execute the remediation commands: it only runs `bash -n` and, with `--check-cli`, `aws <service> <operation> help` (local help, no traffic to AWS).
- If a fix is missing (a `FAIL` finding with no commands, verification `gaps`), it is reported as missing. An ad hoc `aws` one is not invented.

**Only what is verified carries a fix.** `FAIL`, `DOCUMENTED_GAP` and a `DRIFT` or an `UNDOCUMENTED` with `actual_status: FAIL` keep steps and commands. In `DOCUMENTED_ONLY`, `PASS`, `N/A`, `NOT_VERIFIED` and the other `DRIFT` and `UNDOCUMENTED` the assembler leaves `steps: []` and `commands: []`, leaves only `verify_after` (the HTML presents it as "Verify with") and adds `note_status`: "not verified: do not apply without confirming" (and leaves `kind`, `risk` and `downtime` as `null`: there is nothing pending to apply). For example, a `DOCUMENTED_ONLY` for RDS encryption does not show the migration with downtime. Claude does not reconstruct those commands nor mention them as something to apply. The verification (step 9) evaluates every finding with commands, `DOCUMENTED_GAP` included, which is why the `__FILL_IN_*__`, the stamps and the apply order cover them.

## 2. The four `kind`s

| `kind` | What it is | What Claude does |
|---|---|---|
| `cli` | One or a few commands that fix the problem with no decisions from the user. | Review dependencies in the vault; if risk is `medium`/`high`, a verification claim. |
| `cli_with_decision` | There is a value the user decides (retention days, owner email, office CIDR, a key's ARN), the fix turns on a billable feature (GuardDuty protections, Security Hub, PITR, log ingestion) or restarts something (IMDSv2 on running instances, automatic minor upgrades), or the command replaces an existing configuration or policy and it must be read first. The command carries `__FILL_IN_<NAME>__` and/or a prior read-only block, and `notes` explains the decision and warns. Blocks are copied one at a time, never with "Copy all". | Ask for or remember the value; **do not invent it** nor "fill it in" with a plausible value. |
| `planned_change` | Multi-step, destructive or with downtime (encrypting an existing RDS, migrating a key, reducing IAM permissions). It carries numbered `steps`, a warning in `notes`, `risk` and `downtime`. | Explain that it is a planned change and not a one-liner; never present it as "one command". Review against the vault what depends on the resource. |
| `console_only` | Cannot be done by CLI (root MFA, console settings). `steps` in plain language, no commands. | Pass the steps as they are; do not write "equivalent" commands. |

`remediation.risk` is `low` \| `medium` \| `high`; `downtime` is a boolean; `verify_after` is the read-only command to check the fix.

Catalog rules (validated by `validate_catalog.py`): every fix that is not `console_only` has `verify_after`; every `planned_change` has at least 2 steps and `notes` with the warning.

## 3. Placeholders, variables and values to fill in

- **Variables at the top of each block:** `REGION="…"` and `ACCOUNT_ID="…"`, and whatever the block needs (`SG_ID`, `DB_ID`, `TRAIL_NAME`…) in double quotes. The rest of the block uses them as `"$REGION"`.
- **Catalog placeholders**, resolved by `assemble_findings.py` with flat substitution: `{resource_id}`, `{region}`, `{account_id}`, `{resource_name}`, `{resource_arn}` and `{detail_json:<key>}` (the JSON of `detail[<key>]` in single quotes, for commands with the exact rule, for example `--ip-permissions` with only the offending rules).
- **Unknown or unsafe value:** stays as `__FILL_IN_<NAME>__` (for example `__FILL_IN_OWNER_EMAIL__`, `__FILL_IN_KMS_KEY_ARN__`). Also if the value carries quotes, spaces, `$`, backticks or line breaks (it is not injected into a command). The HTML highlights and counts them; `verify_remediation.py` marks them `REVIEW` and adds them to `fill_in_pending`.
- **An unresolved `{placeholder}`** that reaches the HTML is a `CONFLICT`: it is not delivered; review the claim (`resource.id`, `region`) and assemble again.
- The format is `__FILL_IN_<NAME>__` and **not** `<<FILL IN: …>>`: in bash `<<` opens a heredoc and hangs the CloudShell session. A `<<` in a command is a `CONFLICT` of hygiene.

## 4. Command hygiene

- **No `set -e`:** it would close the CloudShell session on the first error. It is a `CONFLICT` of hygiene.
- **Chain with `&&`** every destructive line or one that depends on the previous one (`create-db-snapshot … && aws rds wait … && …`). Idempotent "create" commands that may fail because they already exist go on their own.
- **Read before replacing, and stop if it could not be read.** A fix that replaces a policy or configuration (password policy, bucket policy, key policy, Config delivery channel) carries a first read-only block that saves the current one to a file, a second that merges without applying and shows the result, and a third that applies only the reviewed file. On a read error (for example `AccessDenied`) the block deletes the file and shows `STOPPED`, and the following ones apply nothing; "does not exist yet" (`NoSuchEntity`, `NoSuchBucketPolicy`) starts from an empty policy. A change that leaves the service unreachable if a precondition is missing (HTTP→HTTPS redirect with no 443 listener) checks it in the command itself and stops. Temporary files carry the resource id. A resource replacement (EBS volume, RDS database) never loses data: writes are stopped before the snapshot and the replica is no more exposed than the original (`--no-publicly-accessible`).
- **Alternatives are not copied together:** if two blocks are mutually exclusive ("instance" or "cluster"), they go as a single conditional block or the fix is not `cli`.
- **Never `--force`, `--delete`, `s3 rm`/`s3 rb`, nor `delete-*`, `terminate-*`, `deregister-*`, `detach-*`, `disable-*`, `stop-*`, `remove-*`, `revoke-*` nor commands that replace a whole configuration or policy (`put-*-policy`, `put-bucket-*` such as `put-bucket-acl`, `put-bucket-lifecycle-configuration`, `put-bucket-logging`, `put-bucket-notification-configuration`, `put-bucket-tagging`, `put-public-access-block` (bucket and account), `untag-resources` (and every `untag-*`), `update-account-password-policy`, `update-assume-role-policy`, `replace-*`, and the `modify-*` that rewrite a list: `modify-instance-attribute`, `modify-network-interface-attribute`, `modify-listener`, `modify-rule`) without the matching warning:** the fix must be `planned_change`, or `cli_with_decision` with `notes` that contain a real warning (warning, risk, "replaces", "deletes", "irreversible", "leaves without access", downtime…: the list is in `WARNING_WORDS` of `verify_remediation.py`; arbitrary notes are not enough). Otherwise the verifier marks it `REVIEW` (`destructive_without_warning`). A command that looks like one line and destroys data or access is a design error; Claude does not rewrite it, it flags it in `verification-claims.json` and warns the user.
- **Revoke with the exact rule**, not with broad filters: the catalog builds `revoke-security-group-ingress` with the JSON of the offending rules, not a generic `--cidr 0.0.0.0/0`.
- **Do not overwrite shared policies** (SNS, SQS, bucket, key policy): the fix must add the statement, not replace the document. A replaced key policy can leave the key inaccessible: keep the account root statement.
- **Beware of known side effects:** an apex TXT `UPSERT` can overwrite other TXT values; forcing DKIM rotation changes the tokens and CNAMEs; `--apply-immediately` also applies other pending changes. If the vault shows that the resource uses them, it goes as a verification claim.

## 5. What Claude reviews in the verification stage

For every `FAIL` finding with `REVIEW`/`CONFLICT` and for every `medium` or `high` fix present in `per_finding` of `verification.json` (verify-only ones are not there): what depends on the resource according to the vault and the inventory (a Lambda that uses the key, a service that comes in through the SSH that is being closed, an HTTP client that uses the bucket), and whether the vault has an opposing recommendation. Result: `verification-claims.json` (schema in `references/report-format.md`). A script `CONFLICT` is never lowered.

Initial conflict rules (`references/conflict-rules.json`): closing port 80 (or all traffic) of an SG used by a load balancer of any type, ALB, NLB or classic (`CR-001`), CloudTrail with a CMK without permission in the key policy (`CR-002`), revoking SSH/RDP without SSM (`CR-003`), IMDSv2 with old SDKs (`CR-004`), rotating or disabling access keys in use (`CR-005`), `Deny` without TLS on S3 (`CR-006`), encrypting an existing resource with migration and downtime (`CR-007`), removing `VantaNonProd` from a production resource (`CR-008`), `put-key-policy` (`CR-009`), Multi-AZ with cost and brief failover (`CR-010`).

## 6. How to explain it to the user

- Apply **in the suggested order** (`apply_order`): identity, logging and detection (visibility before touching anything), KMS keys, encryption, network, data and backups, monitoring, tags and integration; `planned_change` last in each group.
- Fill in every `__FILL_IN_*__` before pasting; do not paste blocks with an unresolved `CONFLICT`.
- The "Copy low-risk fixes" button groups only low-risk `cli` fixes, with no pending values, that the verification stamps `OK` (it excludes `REVIEW`, `CONFLICT` and those with no stamp); without a current verification (never run or stale) it is disabled and says why; they are still read before pasting.
- A `risk: high` fix never comes out `OK`: the floor is `REVIEW` ("high risk: pending review against the vault before applying"). If a rule needs a datum the run did not bring (for example `CR-003` with no `CMP-006` result for an instance that uses the security group), the fix stays `REVIEW` with "missing evidence" and the missing item appears in `gaps`. "Copy all" (a card's blocks at once) exists only for `cli` fixes: a `cli_with_decision` or a `planned_change` is copied and applied block by block, reading each one.
- A fix that declares `downtime: true` never comes out `OK`: the floor is `REVIEW` ("the fix declares downtime"), so it does not enter the low-risk copy either.
- If `assemble_findings.py` is run again after verifying, the report shows "stale verification": repeat `verify_remediation.py` and render again.
- After applying, run each card's "Verify afterwards" command, or run the audit again.
- "Do not touch without review" resources: changing them can turn tests that pass today red; the card lists which ones.
- If the vault recommends savings that break tests (turning off Multi-AZ, deleting Flow Logs, deleting the CloudTrail access-logs destination bucket), the report marks it `DRIFT` `high` with "this vault recommendation would break <test>": tell the user; it is not applied.
